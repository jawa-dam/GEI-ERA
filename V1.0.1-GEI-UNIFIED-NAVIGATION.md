# GEI Platform V1.0.1 — Unified Navigation & Module Integration

## Purpose

V1.0.1 turns the V1.0 Platform Core from an isolated hub into a shared integration layer for the existing GEI modules.

## Implemented

- Canonical module registry: `platform/platform-registry.js`
- Shared integration layer: `platform/platform-integration.js`
- Research Engine connected to Platform Core
- Commerce + Vault connected to Platform Core
- Laboratory connected to Platform Core
- Media Engine connected to Platform Core
- Content Explorer connected to Platform Core
- Responsive unified navigation is injected into integrated module pages
- Active module state is written through `GEIPlatform.navigate()`
- Navigation history continues to use the Platform Core browser state model
- Module routes remain provider-neutral and do not grant authentication, payment, or protected access

## Integrity Boundaries

The unified navigation is an application integration layer, not an authority layer.

- Local browser state is not authentication.
- Local browser state is not payment proof.
- Commerce remains provider-neutral.
- Research records continue to distinguish source material, evidence, claims, interpretations, provenance, and review state.
- Laboratory interactions remain conceptual educational models.

## Acceptance Criteria

- Existing module engines continue to load without external runtime dependencies.
- Integrated module pages can discover the Platform Core automatically.
- A single navigation surface exposes the GEI system map.
- Active module state is synchronized through the shared Platform Core.
- Mobile navigation remains horizontally usable without forcing a desktop layout.
- No payment credentials are introduced into client code.
- No claim is made that V1.0.1 provides authentication, production checkout, or protected media delivery.

## Next Logical Build

**V1.0.2 — GEI Shared Identity & Session Layer** should be considered only after the unified navigation is verified in the browser. It would define a non-authoritative visitor/session model first, then prepare the architecture for future server-backed identity without treating localStorage as secure identity.
