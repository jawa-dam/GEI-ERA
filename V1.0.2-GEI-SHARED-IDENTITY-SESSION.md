# GEI Platform V1.0.2 — Shared Identity & Session Layer

## Purpose

V1.0.2 establishes a shared anonymous visitor identity and local session interface for GEI platform surfaces. It creates continuity across module navigation without pretending that browser state is secure identity.

## Implemented

- `platform/platform-session.js` provides the shared session API.
- Persistent anonymous `visitorId` and local `sessionId` identifiers.
- Session creation and last-active timestamps.
- Page-view and module-visit counters.
- Current-module tracking through `gei-platform:navigate`.
- Optional display name with length and character sanitization.
- Self-selected persona values: `visitor`, `learner`, or `researcher`.
- Migration-safe normalization of stored state.
- Shared events: `gei-session:ready`, `gei-session:change`, `gei-session:module`, and `gei-session:reset`.
- Explicit API methods for future server-backed identity integration.

## API

`window.GEI_SESSION` exposes:

- `getState()`
- `getIdentity()`
- `getProfile()`
- `touch()`
- `setProfile({ displayName, persona })`
- `recordModuleVisit(moduleId)`
- `reset()`
- `clear()`
- `isAuthenticated()` — always `false` in V1.0.2
- `isAuthoritative()` — always `false` in V1.0.2

## Storage

The browser storage key is `gei-session-v1.0.2`.

The stored model contains only non-sensitive continuity data. V1.0.2 must not store passwords, payment credentials, secret tokens, or other sensitive authentication material.

## Integrity Boundary

V1.0.2 does **not** provide:

- Authentication
- Authorization
- Verified identity
- Payment verification
- Server-side session security
- Verified researcher credentials

A locally selected `researcher` persona is a profile preference, not a credential or institutional affiliation.

Browser localStorage can be cleared, modified, copied, or unavailable. It therefore remains convenience state only.

## Future Server-Backed Identity

The public interface is intentionally small so a future release can map the local visitor/session model to a trusted backend identity service. That future layer should introduce secure authentication, server-side authorization, signed sessions, and provider-verified entitlements without treating the current local state as proof.

## Acceptance Criteria

1. A visitor identifier persists across GEI module navigation and reloads.
2. Session timestamps and activity counters remain available across modules.
3. Platform navigation updates the current module and visit history.
4. Profile input is bounded and sanitized.
5. Invalid stored data is normalized safely.
6. No sensitive credentials are stored.
7. Local identity is explicitly non-authoritative.
8. Existing V1.0/V1.0.1 module boundaries remain intact.
9. The architecture is ready for a future trusted identity provider without claiming that provider integration exists today.
